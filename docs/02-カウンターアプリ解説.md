## 1. なぜカウンターを作るのか

前回の課題4で、端末を回転させたときのログを見ました。

```
onPause → onStop → onDestroy → onCreate → onStart → onResume
```

**Activity が破棄され、作り直されています。**

ここで当然の疑問が生まれます。

> **Activity が死ぬなら、そこに持たせていた値はどうなるのか？**

答えは「**消えます**」。そして、それをどう防ぐかが Android の状態管理です。

iOS 経験者にとってここは完全に新しい概念です。
`UIViewController` は回転しても死なないので、**この問題自体が存在しません。**

このアプリは、**3つの解決策を1画面に並べて、回転させたときの違いを目で見る**ためのものです。

## 2. 実機で確認した結果

SH-51C（Android 14）で実測した結果です。
3つとも `+1` を3回押してから操作しました。

### 画面を回転させる

| | 回転後 |
|---|---|
| ① `remember` | **0**（消えた） |
| ② `rememberSaveable` | 3（残った） |
| ③ `ViewModel` | 3（残った） |

このときのライフサイクルログ：

```
onPause → onStop → onDestroy → onCreate → onStart → onResume
```

**Activity は確かに破棄されているのに、②と③は値を保っています。**

### プロセスを強制終了させる

ホームボタンでバックグラウンドに送り、`adb shell am kill` でプロセスを殺してから復帰させました。
これは**メモリ不足時に OS が実際に行う動作**のシミュレーションです。

| | プロセス破棄後 |
|---|---|
| ① `remember` | **0** |
| ② `rememberSaveable` | **3**（残った） |
| ③ `ViewModel` | **0**（消えた） |

**②と③の違いがここで出ます。**
`ViewModel` は回転には強いが、**プロセスが殺されると一緒に消えます**。

## 3. Compose の状態管理の基礎

### 「状態」とは何か

Compose では、**状態が変わると UI が自動的に描き直されます**。
この描き直しを **recomposition（再コンポーズ）** と呼びます。

```
状態が変わる → recomposition が走る → 画面が更新される
```

SwiftUI で `@State` の値を変えると `body` が再評価されるのと同じ仕組みです。

### なぜ普通の変数ではダメなのか

```kotlin
// ❌ これでは画面が更新されない
var count = 0
Button(onClick = { count++ }) { Text("$count") }
```

これは動きません。`count` はただの `Int` なので、
**変更されたことを Compose が知る手段がない**からです。

```kotlin
// ✅ mutableIntStateOf を使う
var count by remember { mutableIntStateOf(0) }
```

`mutableIntStateOf` が返すのは **「監視できる箱」** です。
中身が書き換わると Compose に通知が飛び、その値を読んでいる部分だけが再描画されます。

### `by` は何をしているのか

```kotlin
var count by remember { mutableIntStateOf(0) }   // by あり
val count = remember { mutableIntStateOf(0) }    // by なし
```

`by` を付けると、**箱の中身を直接読み書きしているように書けます**。

| | 読むとき | 書くとき |
|---|---|---|
| `by` あり | `count` | `count = 5` |
| `by` なし | `count.value` | `count.value = 5` |

Swift の property wrapper（`@State var count`）が
`_count.wrappedValue` を隠してくれるのと同じ発想です。

`by` を使うには次の2つの import が必要です。忘れるとコンパイルエラーになります。

```kotlin
import androidx.compose.runtime.getValue
import androidx.compose.runtime.setValue
```

### `mutableStateOf` と `mutableIntStateOf`

```kotlin
mutableStateOf(0)      // 汎用。Int はボックス化される
mutableIntStateOf(0)   // Int 専用。ボックス化しない（推奨）
```

`Int` / `Long` / `Float` / `Double` には専用版があり、
そちらのほうが効率的なので**数値には専用版を使うのが推奨**です。

## 4. ① remember

```kotlin
var rememberCount by remember { mutableIntStateOf(0) }
```

### 何をしているのか

**`remember` は「recomposition をまたいで値を覚えておく」ための仕組み**です。

`@Composable` 関数は、状態が変わるたびに**何度も呼び直されます**。
`remember` がないと、呼び直しのたびに `mutableIntStateOf(0)` が実行され、
**毎回 0 に初期化されてしまいます**。

```kotlin
// ❌ remember なし → 押しても 0 のまま
var count by mutableIntStateOf(0)

// ✅ remember あり → 値が保持される
var count by remember { mutableIntStateOf(0) }
```

### なぜ回転で消えるのか

`remember` が値を覚えている場所は **Composition（画面を構成しているツリー）の中**です。

**Activity が破棄されると、Composition ごと消えます。**

```
回転
  ↓
Activity.onDestroy    ← Composition も一緒に破棄される
  ↓
Activity.onCreate     ← Composition を新規作成
  ↓
remember { mutableIntStateOf(0) } が再実行される → 0
```

つまり `remember` は **「Activity が生きている間だけ」** の記憶です。

> **⚠️ より正確には「Composition 上でその呼び出し位置が存在し続けている間」です。**
>
> Activity の破棄はその一番大きなケースにすぎません。例えば
> `if (show) { /* ここに remember */ }` と書いた場合、`show` が `false` になった時点で
> その state は消えます。`LazyColumn` でスクロールアウトしたときも同様です。
>
> **カメラ画面をタブや条件分岐の中に置いた途端に挙動が変わる**ので、
> Phase 2 に入る前に押さえておいてください。

### キーを指定して作り直す

`remember` は**キー**を渡せます。キーが変わると、覚えていた値を捨てて作り直します。

```kotlin
// lensFacing が変わったら、カメラの設定を作り直す
val config = remember(lensFacing) { buildCameraConfig(lensFacing) }
```

**Phase 2 で「前面カメラ / 背面カメラの切り替え」を実装するときに必ず使う形**です。
`LaunchedEffect(lensFacing)` も同じ考え方で動きます。

### SwiftUI との対応

**SwiftUI の `@State` に最も近い**のがこれです。

ただし SwiftUI の `@State` は回転で消えません（そもそも View が破棄されないため）。
**「@State + Android では回転で消える」** と覚えるのが実態に合っています。

## 5. ② rememberSaveable

```kotlin
var saveableCount by rememberSaveable { mutableIntStateOf(0) }
```

### 何が違うのか

`remember` の機能に加えて、**値を `Bundle` に保存します**。

`Bundle` は Android が用意する「一時的な保存箱」です。
**システム主導で** Activity が破棄されるとき（回転、メモリ不足など）に
`onSaveInstanceState` で書き出され、再生成時の `onCreate(savedInstanceState)` で戻ってきます。

**`onSaveInstanceState` は常に呼ばれるわけではありません。**
ユーザーが戻るボタンで閉じた場合や `finish()` の場合は呼ばれません
（＝ユーザーが意図的に終わらせたので、復元する必要がないという考え方です）。

```
回転
  ↓
値を Bundle に保存 ────────┐
Activity.onDestroy         │
Activity.onCreate          │
  ↓                        │
Bundle から値を復元 ←──────┘  → 3
```

**この Bundle は OS が保持するので、アプリのプロセスが死んでも残ります。**
だからプロセス破棄からも復帰できます。

> **⚠️ ただし、いつでも残るわけではありません。**
>
> 効くのは「タスクが最近使用したアプリ一覧に残っている」場合だけです。
> 次のいずれかで保存状態は**破棄されます**。
>
> - ユーザーが最近使用したアプリ一覧から**スワイプして消す**
> - 設定から**強制停止**する（`adb shell am force-stop`）
> - **端末を再起動**する
> - **戻るボタンで画面を閉じる**（`finish()` 相当。この場合 `onSaveInstanceState` は呼ばれません）
>
> 課題2 で使う `am kill`（OS のメモリ不足を模した終了）とは**扱いが違います**。
> 「試したら消えた」の原因はほぼこれです。

### 制約

**何でも保存できるわけではありません。**

保存できるのは `Bundle` に入れられる型だけです。

| 保存できる | 保存できない |
|---|---|
| `Int` `Long` `Float` `Boolean` `String` | 独自クラス（そのままでは不可） |
| `Parcelable` / `Serializable` を実装した型 | ラムダ、コールバック |
| それらの配列・リスト | 巨大なデータ |

**サイズ制限が厳しい**のも重要な点です。
`Bundle` はプロセス間通信を経由するため、
大きすぎると `TransactionTooLargeException` でアプリが落ちます。

> **目安：数百KB を超えるものは入れない。**
> 画像やリスト全件のようなデータは `rememberSaveable` に置いてはいけません。
>
> Binder のトランザクションバッファは**プロセス全体で共有される約 1MB** で、
> 同時に走る他の通信とも分け合うため、実効上限は 1MB よりかなり小さくなります。
> Android 7.0 (API 24) 以降は超過時に黙って失敗せず、例外で落ちます。

独自クラスを保存したい場合は `Saver` を自作する必要があり、手間が増えます。

> **なぜ `mutableIntStateOf(0)` は `Saver` なしで動くのか**
>
> Compose の state 実装（`ParcelableSnapshotMutableIntState`）自体が `Parcelable` であり、
> 中身の `Int` が Bundle に入れられる型だからです。
> 逆に言えば、**中身が Bundle に入らない型だと実行時に落ちます**。

## 6. ③ ViewModel

```kotlin
val vm: CounterViewModel = viewModel()
```

### 発想が違う

①②は「Activity の中で何とかする」方法でした。
`ViewModel` は **状態を Activity の外に置く**という発想です。

```
       ┌──────────────┐
       │  ViewModel   │  ← 回転しても生き続ける
       │  count = 3   │
       └──────┬───────┘
              │ 参照
   ┌──────────┴──────────┐
   │  Activity（回転で作り直される）│
   └─────────────────────┘
```

Activity が破棄・再生成されても、**`viewModel()` は同じインスタンスを返します**。
だから値がそのまま見えます。

### なぜそんなことが可能なのか

`ViewModel` は `ViewModelStore` という保管庫に置かれ、
**この保管庫は設定変更をまたいで引き継がれる**ようになっています。

Android フレームワークが「回転のときは ViewModelStore を持ち越す」という
特別扱いをしている、と理解してください。

### いつ破棄されるのか

**「画面が本当に終了したとき」だけ**です。

| 操作 | ViewModel |
|---|---|
| 画面回転 | **生き残る** |
| ホームボタン → 復帰 | 生き残る |
| 戻るボタンで画面を閉じる | **破棄される**（`onCleared()` が呼ばれる） |
| OS にプロセスを殺される | **消える** |

このプロジェクトの `CounterViewModel` には `onCleared()` にログを入れてあるので、
`adb logcat -s LIFECYCLE` で観察できます。**回転では呼ばれません。**

### ⚠️ `ViewModel` に `Context` や `Activity` を持たせてはいけない

`ViewModel` は Activity より長生きします。ということは、
**`ViewModel` に Activity への参照を持たせると、破棄されたはずの Activity が
メモリ上に残り続けます**（メモリリーク）。

```kotlin
// ❌ やってはいけない
class MyViewModel(private val activity: Activity) : ViewModel()
class MyViewModel : ViewModel() { var context: Context? = null }
```

**Phase 2 でほぼ全員が通る道**です。`ProcessCameraProvider` や `Context` を
`ViewModel` に置きたくなりますが、置いてはいけません。
Context が必要なら、Composable 側で `LocalContext.current` から取って渡します
（アプリ全体で1つの `Application` Context なら `AndroidViewModel` で持てます）。

### プロセス破棄には勝てない

実測で確認したとおり、`am kill` でプロセスを殺すと `ViewModel` の値は消えます。

**`ViewModel` はメモリ上のオブジェクトにすぎず、プロセスが死ねば道連れ**だからです。

これに対応するには `SavedStateHandle` という仕組みを使い、
`ViewModel` の中で Bundle に保存します（今回は扱いません）。

## 7. 3つの使い分け

### 実測に基づく比較表

| | 再描画 | **画面回転** | **プロセス破棄** | 保存できる量 |
|---|---|---|---|---|
| **① `remember`** | ✅ | ❌ | ❌ | メモリの許す限り |
| **② `rememberSaveable`** | ✅ | ✅ | △（下記参照） | **数百KB まで** |
| **④ `ViewModel` + `SavedStateHandle`** | ✅ | ✅ | ✅ | 小さい値のみ |
| **③ `ViewModel`** | ✅ | ✅ | ❌ | メモリの許す限り |

### 実務での選び方

```
その状態は、画面を閉じたら消えていい？
├─ YES ─→ 画面内で完結する一時的なもの？
│          ├─ 回転で消えてもいい（スクロール中のアニメ状態など）
│          │    → ① remember
│          └─ 回転では残ってほしい（入力中のテキスト、選択中のタブ）
│               → ② rememberSaveable
└─ NO ──→ 画面全体のデータ、通信結果、複雑なロジック
           → ③ ViewModel（＋必要なら DB や DataStore に永続化）
```

**目安：**

- **① `remember`** … UI の見た目に関する一時状態（開閉、アニメーション）
- **② `rememberSaveable`** … 小さくて失うと困る値（入力途中のテキスト、選択位置）
- **③ `ViewModel`** … 画面のデータ本体、API 通信の結果、ビジネスロジック

**②と③は排他ではありません。** 実務では
「データ本体は `ViewModel`、UI の細かい位置は `rememberSaveable`」のように併用します。

### 本当に失いたくないデータは

3つとも **アプリを完全に終了すると消えます**。

本当に永続化したいなら、`DataStore`（設定値）や `Room`（データベース）を使います。
これは Phase 2 以降の話題です。

## 8. コードを読む

### `CounterViewModel.kt`

```kotlin
class CounterViewModel : ViewModel() {

    var count by mutableIntStateOf(0)
        private set                      // ★外からは書き換えられない

    fun increment() { count++ }
    fun reset() { count = 0 }

    override fun onCleared() {
        super.onCleared()
        android.util.Log.d("LIFECYCLE", "ViewModel.onCleared  ← ViewModel が破棄された")
    }
}
```

**`private set` がポイント**です。

- **読む**のは外から自由（`vm.count`）
- **書く**のは `increment()` / `reset()` を通してのみ

これにより「状態の変更経路を1か所に集約」できます。
UI から `vm.count = 100` と直接書かれる余地をなくす、という設計です。

Swift の `private(set) var` と同じ考え方です。

### `CounterScreen.kt`

```kotlin
@Composable
fun CounterScreen(modifier: Modifier = Modifier) {
    var rememberCount by remember { mutableIntStateOf(0) }
    var saveableCount by rememberSaveable { mutableIntStateOf(0) }
    val vm: CounterViewModel = viewModel()
    ...
}
```

`viewModel()` は **`androidx.lifecycle.viewmodel.compose`** の関数で、
「`ViewModel` を取得する（無ければ作る）」という動作をします。

**厳密には `LocalViewModelStoreOwner.current` に紐づきます。**
このアプリでは画面が1枚なので **`MainActivity` に紐づいている**状態です。
将来 Navigation を入れると「画面（`NavBackStackEntry`）ごと」に変わるので、
「この画面に紐づく」という理解のままだと後で混乱します。

そのため `build.gradle.kts` に依存を追加してあります。

```kotlin
implementation(libs.androidx.lifecycle.viewmodel.compose)
```

### `CounterCard` — 部品の切り出し方

同じ見た目のカードを3つ並べるため、`CounterCard` という部品に切り出しています。

```kotlin
@Composable
private fun CounterCard(
    index: String,
    title: String,
    description: String,
    expectation: String,
    count: Int,                  // ← 値を受け取る
    onIncrement: () -> Unit,     // ← 操作は関数で受け取る
    onReset: () -> Unit,
) { ... }
```

**`CounterCard` 自身は状態を持ちません。**
値をもらって表示し、押されたことを親に伝えるだけです。

これを **ステートレス（stateless）なコンポーザブル**と呼び、Compose の基本作法です。

- 状態を持つのは親（`CounterScreen`）だけ
- 部品は「表示」と「イベント通知」に徹する
- → 部品が再利用しやすく、テストしやすくなる

この「状態を上に集める」考え方を **state hoisting（状態の巻き上げ）** といいます。
SwiftUI で `@Binding` を使って親に状態を持たせるのと同じ発想です。

## 9. iOS との比較

| 観点 | iOS | Android |
|---|---|---|
| 回転で画面が破棄されるか | **されない** | **される** |
| 一時的な UI 状態 | `@State` | `remember` |
| 復元したい小さな値 | （問題が起きないので概念が薄い） | `rememberSaveable` |
| 画面のデータ本体 | `@StateObject` / `ObservableObject` | `ViewModel` |
| プロセス破棄からの復元 | State Restoration（任意） | `rememberSaveable` / `SavedStateHandle` |
| 状態を親に持たせる | `@Binding` | state hoisting（引数と `onXxx`） |

### なぜ Android はこんな設計なのか

一言でいうと **メモリが厳しい環境で育ったから**です。

- 端末の性能差が非常に大きい（安価な端末も多い）
- バックグラウンドのアプリは**積極的に殺される**前提
- 画面回転だけでなく、言語変更・ダークモード切替・フォントサイズ変更でも
  同じ「設定変更」が起きる

そのため **「Activity はいつでも死にうる」** を前提に設計されています。
面倒に見えますが、**復元処理を最初から強制される**ので、
「バックグラウンドから戻ったら壊れていた」という不具合は起きにくくなります。

iOS 経験者としては、**`ViewModel` は `@StateObject` に相当する**と考えるのが
一番しっくりくると思います。

## 10. 手を動かして確かめる

### 課題1：3つの違いを体感する（10分）

1. 3つとも `+1` を数回押す
2. **端末を回転させる** → ①だけ 0 に戻ることを確認
3. `adb logcat -s LIFECYCLE` を流しながら回転させ、
   `onDestroy → onCreate` が起きているのに②③が残ることを確認

```bash
adb logcat -s LIFECYCLE
```

### 課題2：プロセス破棄を再現する（10分）

②と③の違いを見ます。

```bash
# 1. 3つとも増やす
# 2. ホームボタンを押してバックグラウンドへ
adb shell input keyevent KEYCODE_HOME

# 3. OS がメモリ不足で殺す状況を再現
adb shell am kill com.example.xrstudy

# 4. アプリに戻る
adb shell am start -n com.example.xrstudy/.MainActivity
```

**②だけが残り、③は 0 に戻ります。**

> **手順4は「最近使用したアプリ一覧から戻る」か「ホーム画面のアイコンをタップ」でも構いません。**
> むしろそちらのほうが確実です（`am start` はタスクの再利用に依存するため、
> 環境によっては新しいタスクとして起動して②も消えることがあります）。
>
> **なお、最近使用したアプリ一覧から「スワイプして消す」と②も消えます。**
> これは「ユーザーが意図的に終わらせた」扱いになり、保存状態が破棄されるためです。

> `am kill` はバックグラウンドのアプリにしか効きません。
> 前面にあるまま実行しても何も起きないので、必ずホームに戻してから実行してください。

### 課題3：`remember` を外してみる（5分）※戻すこと

`CounterScreen.kt` の①を次のように変えます。

```kotlin
// var rememberCount by remember { mutableIntStateOf(0) }
var rememberCount by mutableIntStateOf(0)      // remember を外す
```

ビルドして `+1` を押してください。**数字が増えません。**

理由はこうです。

1. `+1` を押す → 前回のコンポジションで作られた state に書き込まれる
2. その state を読んでいるので **再コンポーズが1回走る**
3. その中で `mutableIntStateOf(0)` が**再実行され、新しい 0 の state に置き換わる**
4. 表示は 0 のまま

> 無限ループではありません。**押すたびに1回だけ再コンポーズが起き、そのたびに 0 で作り直される**、
> というのが正確な説明です。

**`remember` が「呼び直しをまたいで覚える」ためのものだと体感できます。**

> **⚠️ Android Studio が `UnrememberedMutableState` という警告（赤い波線）を出します**が、
> **デバッグビルドは通ります**。警告は無視してそのまま実行してください。

確認したら元に戻してください。

### 課題5：state hoisting を壊してみる（15分・発展）

`CounterCard` の中に状態を持たせてしまうと何が起きるかを見ます。

`CounterCard` の中に state を追加し、**既存の `count` / `onIncrement` を使っている箇所を
置き換えます**（追加ではなく置き換えです。追加するとボタンが2個並ぶだけになります）。

```kotlin
@Composable
private fun CounterCard(
    index: String, title: String, description: String, expectation: String,
    count: Int, onIncrement: () -> Unit, onReset: () -> Unit,
) {
    var localCount by remember { mutableIntStateOf(0) }   // ★部品側に状態を持たせる

    Card(...) {
        Column(...) {
            ...
            Row(...) {
                Text(text = "$localCount", ...)              // count → localCount
                Button(onClick = { localCount++ }) { Text("+1") }   // onIncrement → localCount++
                OutlinedButton(onClick = onReset) { Text("リセット") }  // ここは変えない
            }
        }
    }
}
```

**観察すること：**

1. 3つのカードが**それぞれ独立して**カウントする（親は値を知らない）
2. **「リセット」ボタンが効かなくなる** — `onReset` は親の state を 0 にしますが、
   表示している `localCount` は変わりません

②が「**親から制御できなくなる**」ことの最も分かりやすい証拠です。
これが state hoisting をする理由です。確認したら元に戻してください。
